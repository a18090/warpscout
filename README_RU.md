## Что это

У Cloudflare WARP тысячи адресов эндпоинтов, и выбрать, где именно выйдет туннель, штатными средствами нельзя. WARPSCOUT проверяет эти адреса по очереди и для каждого показывает, из какой страны виден трафик и на какой пограничный узел Cloudflare попал туннель. Попутно измеряются задержка и потери пакетов, так что среди удачно расположенных эндпоинтов можно выбрать ещё и быстрый.

### Чем важен узел

Ради выбора узла инструмент и написан. С апреля 2026 года трафик через московский узел (`DME`) фильтруется DPI внутри России: часть сайтов и сервисов через него просто не открывается, хотя сам WARP подключается нормально. Тот же конфиг, направленный на эндпоинт с другим узлом, работает без этой проблемы.

В официальном клиенте WARP такой настройки нет. Узел зависит и от местоположения, и от адреса эндпоинта, к которому идёт подключение, поэтому выбрать его можно только одним способом: проверить адреса со своего соединения и посмотреть, куда они попадают. Этим WARPSCOUT и занимается, и ради этого же существуют `-node` и `-country`: сканируем, оставляем только эндпоинты мимо нежелательного узла, выгружаем конфиг для лучшего из них.

### Проверка региона сервера

Второй частый сценарий - VPS. Регион WARP определяет по адресу, с которого приходит подключение, а лежащие в основе этого решения базы GeoIP часто врут: машина, физически стоящая в Нидерландах, может числиться индийской, и такой её будет считать каждый сайт, до которого дотянется туннель.

Скан на сервере отвечает на этот вопрос сразу, колонкой `SEEN AS`. Поднимать WARP и выяснять постфактум, что половина сервисов переехала в другую страну, не приходится.

Насколько подробным получится результат, зависит от расположения сервера. У большинства европейских провайдеров все адреса попадают на один узел с одним регионом, и скан укладывается в экран:

![WARPSCOUT single node](.github/assets/warpscout-single-node.png)

Российские провайдеры менее предсказуемы: одна машина даёт `ARN`, другая `HEL`, а некоторые раздают по пулам четыре локации и больше и на них есть из чего выбирать:

![WARPSCOUT multi-node](.github/assets/warpscout-multi-node2.png)

Поддерживаются два протокола: обычный WireGuard (`wg`) и AmneziaWG (`awg`) - обфусцированная версия WireGuard, которая проходит там, где обычный WireGuard фильтруется.

- Один статический бинарник
- Без root и без TUN-устройства - туннель работает в userspace режиме
- Linux, macOS, Windows и Docker, на `amd64` и `arm64`
- Живая таблица во время скана плюс файл отчёта, пригодный для обработки (например, `awk`)

## Как это работает

Скан идёт в две фазы.

**Фаза 1 - какие порты проходят.** Эндпоинты WARP слушают несколько UDP-портов и молчат в ответ на всё, кроме валидного рукопожатия WireGuard. Поэтому завершённое рукопожатие - единственная надёжная проверка доступности порта. WARPSCOUT берёт несколько адресов и выясняет, какие порты выпускает сеть. Сначала пробуются распространённые, и только если ни один не прошёл, перебираются остальные.

**Фаза 2 - где выходит каждый эндпоинт.** Для каждого адреса поднимается настоящий туннель, а через него запрашивается `https://speed.cloudflare.com/meta`. В одном этом ответе есть всё нужное:

- `SEEN AS` - страна, в которой вас считают находящимся другие сайты
- `NODE` - пограничный узел Cloudflare, на который попал туннель, в виде кода аэропорта
- `NODE LOCATION` - город и страна этого узла

Задержка меряется в той же фазе: адрес эндпоинта пингуется с хоста (`ENDPOINT PING`), а с `-tun-ping` дополнительно измеряются время отклика и потери пакетов внутри туннеля (`TUN PING`, `LOSS`).

Регион выхода и расположение узла - разные вещи. Туннель может идти через Франкфурт и всё равно выходить как Россия. `SEEN AS` отвечает на вопрос, какой регион видят сайты. `NODE` важен, когда речь о задержке или о том, через какую фильтрацию трафик проходит на выходе: узел внутри страны с цензурой может резать или замедлять то, что тот же аккаунт спокойно проносит через узел за границей.

Стоит учитывать, что одна подсеть `/24` может раздавать несколько разных пограничных узлов, и даже соседние адреса иногда отличаются. Считать, что подсеть равна локации, нельзя.

## Установка

### Скачать бинарный файл

Откройте самый свежий релиз на [странице релизов](https://github.com/vernette/warpscout/releases). Там лежат по одному архиву на ОС, выберите свой:

| Ваша ОС                                | Файл                  |
| -------------------------------------- | --------------------- |
| Windows                                | `windows_amd64.zip`   |
| Mac на Apple silicon                   | `darwin_arm64.tar.gz` |
| Mac на процессоре Intel                | `darwin_amd64.tar.gz` |
| Linux, обычный ПК или сервер           | `linux_amd64.tar.gz`  |
| Linux на ARM (Raspberry Pi, часть VPS) | `linux_arm64.tar.gz`  |

**Linux и macOS.** Распакуйте архив и сделайте файл исполняемым:

```sh
tar xzf warpscout_*.tar.gz
chmod +x warpscout
./warpscout register
```

> [!NOTE]
> **Только для macOS.** Первый запуск блокируется, потому что файл скачан из интернета. Снимите этот флаг один раз:
>
> ```sh
> xattr -d com.apple.quarantine warpscout
> ```

**Windows.** Распакуйте `.zip`, откройте PowerShell или командную строку в папке с распакованным файлом (правый клик по папке с зажатым Shift, дальше Open PowerShell/CMD here) и запустите:

PowerShell:

```powershell
.\warpscout.exe register
```

CMD:

```cmd
warpscout.exe register
```

### Собрать самому

С Go 1.25 или новее:

```sh
go install github.com/vernette/warpscout@latest
```

### Docker

```sh
# Регистрация аккаунта WARP
docker run --rm -it --user "$(id -u):$(id -g)" -v "$PWD:/data" vernette/warpscout register

# Скан по обычному WireGuard
docker run --pull always --rm -it --user "$(id -u):$(id -g)" -v "$PWD:/data" vernette/warpscout scan

# Скан по AmneziaWG
docker run --pull always --rm -it --user "$(id -u):$(id -g)" -v "$PWD:/data" vernette/warpscout scan -p awg
```

Зачем нужны эти флаги - см. [Docker](#docker-1).

## Использование

У WARPSCOUT три команды. Полный список флагов любой из них - `warpscout <команда> -h`.

| Команда     | Что делает                                                    |
| ----------- | ------------------------------------------------------------- |
| `register`  | Создать аккаунт WARP и сохранить его. Начинать нужно с этого. |
| `scan`      | Просканировать эндпоинты и показать рабочие.                  |
| `find-junk` | Подобрать настройки AmneziaWG, которые проходят через фильтр. |

### Шаг 1: register

Любому скану нужен аккаунт WARP, так что начать нужно с этого:

```sh
warpscout register
```

Команда записывает `warpscout-account.json` в текущую директорию. Без этого файла `scan` и `find-junk` не запустятся. `-a/-account FILE` кладёт файл в другое место, и тот же флаг подсказывает `scan`, где искать.

#### Как происходит регистрация

WARPSCOUT делает то же, что официальный клиент WARP при первом запуске: регистрирует в Cloudflare новое устройство и получает для него пир WireGuard.

1. Локально генерируется свежая пара ключей X25519. Приватная половина остаётся на машине, где запущена утилита.
2. Публичная половина уходит на `https://api.cloudflareclient.com/v0a4005/reg` под видом Android-клиента. В ответ приходят `id` аккаунта, bearer-токен и публичный ключ пира WARP.
3. Второй запрос включает для этого аккаунта WARP (`warp_enabled: true`).
4. Результат записывается в файл аккаунта:

```json
{
  "id": "...",
  "token": "...",
  "private_key": "...",
  "peer_public_key": "..."
}
```

| Поле              | Что это                                                                                       |
| ----------------- | --------------------------------------------------------------------------------------------- |
| `id`              | Аккаунт, созданный Cloudflare. Адресует последующие запросы.                                  |
| `token`           | Bearer-токен, который эти запросы авторизует. И то, и другое - секреты.                       |
| `private_key`     | Своя сторона туннеля. Она же попадает в конфиги `-conf`.                                      |
| `peer_public_key` | Публичный ключ пира WARP - общий для всех эндпоинтов, поэтому одного аккаунта хватает на все. |

#### Повторный запуск register

При повторном запуске `id` и `token` берутся из файла, а меняются только ключи: генерируется новая пара и уходит через `PATCH`, так что новый `private_key` появляется без ещё одной регистрации. Новый аккаунт создаётся в двух случаях - при `-fresh`, который игнорирует файл целиком, и при неудачной ротации (отозванный токен, удалённый на стороне Cloudflare аккаунт).

#### Когда API недоступен

Обычно это простой процесс, в котором отправляется 2 запроса. В фильтрующей сети эти запросы наружу не уходят вовсе.

WARPSCOUT сначала проверяет, отвечает ли `api.cloudflareclient.com`. Если нет - регистрируется _через_ туннель WARP: перебирает адреса эндпоинтов, поднимает туннель к первому, с которым прошло рукопожатие, и отправляет те же самые регистрационные запросы уже через него. Сначала пробуется AmneziaWG, затем обычный WireGuard, а для AmneziaWG перебирается ещё и несколько разных первых пакетов (`I1`), пока какой-нибудь не пройдёт фильтр.

При наличии прокси `-x/-proxy` отправляет регистрацию через него и запасной путь через туннель вообще не задействуется:

```sh
warpscout register -x socks5://127.0.0.1:1080
```

### Шаг 2: scan

```sh
warpscout scan -p awg
```

`-p/-proto` выбирает протокол: `wg` (по умолчанию), `awg` или `masque`. В сетях, фильтрующих VPN-трафик, обычный `wg` обычно не работает нигде, и стоит сразу использовать `awg` или `masque`, см. [MASQUE](#masque).

Если с `-p awg` не нашлось ни одного рабочего эндпоинта, менять дальше нужно поддельный первый пакет (`I1`), а не junk параметры:

```sh
warpscout scan -p awg -gen-i1 quic
```

Фильтр, который пропускает рукопожатие, а потом убивает туннель, снаружи неотличим от недоступного эндпоинта, и лечится это обычно другим `I1` - см. [Обфускация AmneziaWG](#обфускация-amneziawg). Очередь [`find-junk`](#шаг-3-find-junk-только-если-всё-заблокировано) наступает, только когда не помог ни один профиль `-gen-i1`.

Результаты сортируются сначала по потерям, потом по пингу, так что верхняя строка - лучший эндпоинт. Полезные флаги:

| Флаг                | Что делает                                                                                                                                                                                          |
| ------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `-P, -tun-ping`     | Добавляет колонки `TUN PING` и `LOSS` - RTT и потери, измеренные внутри туннеля - и помечает эндпоинты, которые DPI рвёт посреди передачи. По умолчанию выключено, так как занимает больше времени. |
| `-tun-ping-count N` | Сколько эхо-пакетов на эндпоинт (по умолчанию 10, минимум 5). Включает `-tun-ping`. Чем длиннее серия, тем вернее ловятся туннели, рвущиеся через секунду-другую.                                   |
| `-n, -sample N`     | Сколько адресов пробовать в каждой подсети (по умолчанию 5).                                                                                                                                        |
| `-f, -full`         | Пробовать все 256 адресов каждой подсети. Медленно, но тщательно.                                                                                                                                   |
| `-jt N`             | Сколько туннелей поднимать одновременно (по умолчанию 10).                                                                                                                                          |
| `-t, -timeout N`    | Таймаут на запрос в секундах (по умолчанию 2).                                                                                                                                                      |
| `-6, -ipv6`         | Использовать пулы IPv6-эндпоинтов вместо IPv4.                                                                                                                                                      |
| `-I, -interface`    | Пускать всё через указанный интерфейс (Linux; может понадобиться `CAP_NET_RAW`).                                                                                                                    |
| `-o, -output F`     | Куда писать отчёт (по умолчанию `warpscout-report-<timestamp>.txt`).                                                                                                                                |
| `-no-report`        | Не писать файл отчёта вообще.                                                                                                                                                                       |
| `-emoji`            | Показывать флаги стран рядом с регионами. По умолчанию выключено: терминалы рисуют их по-разному.                                                                                                   |
| `-plain`            | Построчный вывод вместо живой панели.                                                                                                                                                               |

Пингов два и они разнесены по разным колонкам:

| Колонка         | Что меряет                                                                               | Когда видна   |
| --------------- | ---------------------------------------------------------------------------------------- | ------------- |
| `ENDPOINT PING` | ICMP-пинг до самого адреса эндпоинта, прямо с этого хоста. Туннель не задействован.      | всегда        |
| `TUN PING`      | Время отклика до `1.1.1.1` **через** туннель, рядом с `LOSS`, измеренным в той же серии. | с `-tun-ping` |

`ENDPOINT PING` дешёвый и говорит только о том, насколько далеко адрес; к туннелю он отношения не имеет.

Друг с другом эти числа не сравниваются никогда. Всю таблицу ранжирует одно из них: с `-tun-ping` это сначала потери, потом `TUN PING`, без него - только `ENDPOINT PING`.

`ENDPOINT PING` открывает ICMP-сокет и без нужного разрешения показывает `?` (см. [Решение проблем](#решение-проблем)); `TUN PING` работает внутри пользовательского туннеля и не требует привилегий вообще.

Файл отчёта - плоский список: закомментированная шапка, дальше все рабочие эндпоинты, дальше разорванные, в конце лучший эндпоинт каждого пограничного узла. Легко обрабатывается скриптами.

#### Эндпоинты, помеченные как `torn down`

Часть эндпоинтов попадает в отдельный список `torn down` вместо рабочих. Это те эндпоинты, которые сначала работали, а после передачи какого-то числа данных перестали:

1. Рукопожатие проходит нормально.
2. Какое-то время идут данные - в скане это серия пингов, в реальной жизни это был бы ваш трафик.
3. Посреди передачи соединение обрывается, все последующие пакеты теряются, новое рукопожатие тоже не проходит. Туннель мёртв до перезапуска туннеля.

Так DPI поступает с туннелем, который ему не понравился, и поэтому утилита делает серию из 10 эхо-пакетов, а не из двух-трёх: более короткая серия не увидит, что DPI разорвал соединение, и эндпоинт попадёт в полностью рабочие. Проверка намеренно смотрит на _хвост_ подряд потерянных пакетов, а не на процент потерь. Так эндпоинт, теряющий отдельные пакеты, остаётся рабочим с потерями в `LOSS`, а отвалившийся попадает в `torn down`.

Это свойство скорее сети, чем эндпоинта. Там, где WARP ничем не фильтруется - европейский VPS, большинство домашних линков за пределами страны с цензурой, - работает обычный `-p wg`. В России скан по обычному WireGuard может показать пару рабочих подсетей, и каждая из них умрёт сразу после первого рукопожатия. В таком случае поможет `-p awg` с обфускацией.

Увидеть разрыв способен только `-tun-ping`: для наблюдения нужен трафик в туннеле. Разорванные эндпоинты никогда не выбираются `-best` и `-conf` - показывают их затем, чтобы было видно, какую часть пула режет сеть. Из этого можно сделать вывод, что стоит сменить профиль для `I1` через `-gen-i1`.

### Шаг 3: find-junk (только если всё заблокировано)

Если `-p awg` ничего не находит ни с одним профилем `-gen-i1`, значит под сеть надо подгонять и числа junk. `find-junk` ищет рабочий набор:

```sh
warpscout find-junk -gen-i1 random
```

`-gen-i1` стоит добавлять всегда. Junk-пакеты чаще всего не решают проблему, а на практике соединение проходит благодаря поддельному первому пакету, а без `-gen-i1` поиск оставляет его одинаковым на каждой попытке. Что это такое - см. [Обфускация AmneziaWG](#обфускация-amneziawg).

Команда пересканирует раз за разом со свежими случайными настройками, пока какой-нибудь набор не поднимет хотя бы `-threshold` процентов взятых эндпоинтов (по умолчанию 95). Затем печатает готовую строку `warpscout scan ...` с рабочими настройками - остаётся скопировать и запустить сканирование. `Ctrl+C` или `q` в любой момент сохраняет лучший найденный набор.

Работает только с AmneziaWG и проверяет эндпоинты одними рукопожатием и пингом, поэтому колонки региона и узла остаются пустыми.

## Скриптинг

`-best` заменяет таблицы одной строкой `ip:port` в стандартном выводе, и инструмент легко вставляется в скрипт или пайп:

```sh
warpscout scan -p awg -best
# 188.114.98.58:2408
```

Фильтры сужают выборку. `-node` оставляет только эндпоинты, попадающие на заданные узлы, `-country` - только те, чей узел находится в заданных странах. Оба принимают списки через запятую и комбинируются:

```sh
warpscout scan -p awg -country DE,NL -best
warpscout scan -p awg -node HEL,ARN -best
```

Если после фильтров ничего не осталось, команда завершается ошибкой.

`-conf` пишет готовый к импорту конфиг WireGuard или AmneziaWG для единственного лучшего эндпоинта запуска:

```sh
warpscout scan -p awg -country DE -conf warp.conf
```

`-conf -` печатает конфиг в терминал, чтобы можно было скопировать его, либо направить в пайп.

```sh
warpscout scan -p awg -conf -
warpscout scan -p awg -conf - > warp.conf
```

Добавьте `-table-off`, если маршрутизируете трафик сами и не хотите, чтобы конфиг трогал маршруты.

```sh
warpscout scan -p awg -conf warp.conf -table-off
```

`-mtu` задаёт `MTU` в сгенерированном конфиге. Без него строка не пишется вообще и клиент выбирает значение по умолчанию сам.

```sh
warpscout scan -p awg -conf warp.conf -mtu 1280
```

В сгенерированном конфиге по умолчанию прописаны резолверы Cloudflare - `1.1.1.1, 1.0.0.1`, а при использовании `-6` их IPv6-пара. `-dns` заменяет их своим списком через запятую, `-no-dns` убирает строку вообще и клиент оставляет системные резолверы.

```sh
warpscout scan -p awg -conf warp.conf -dns 9.9.9.9,149.112.112.112
warpscout scan -p awg -conf warp.conf -no-dns
```

`-conf-type` выбирает формат конфига. По умолчанию `native` - то, что описано выше: `.conf` для `wg`/`awg` и `config.json` для `masque` под использование с [usque](https://github.com/Diniboy1123/usque). `mihomo` пишет блок `proxies:` для [mihomo](https://github.com/MetaCubeX/mihomo), который умеет и AmneziaWG и MASQUE.

```sh
warpscout scan -p awg -conf warp.yaml -conf-type mihomo
warpscout scan -p masque -conf warp.yaml -conf-type mihomo
```

`-target` сканирует указанные адреса вместо встроенных пулов. Принимает отдельные IP-адреса, целые диапазоны CIDR или любую их смесь через запятую:

```sh
warpscout scan -p awg -target 188.114.98.58
warpscout scan -p awg -target 188.114.98.0/28
warpscout scan -p awg -target 188.114.98.58,162.159.192.0/28
```

Диапазоны IPv4 шире `/20` отклоняются, смешивать IPv4 с IPv6 в одном запуске нельзя.

## Обфускация AmneziaWG

DPI узнаёт WireGuard по рукопожатию. AmneziaWG ломает это двумя способами: подмешивает к настоящему трафику мусорные пакеты и открывает соединение выдуманным первым пакетом (`I1`), который притворяется протоколом, который никто не блокирует.

### Обычно решает первый пакет

Основную работу из этих двух делает `I1`. DPI склонен судить о соединении по тому, как оно начинается, поэтому сессия, открывшаяся чем-то похожим на QUIC или DNS, часто проходит, а она же с другими размерами junk - нет. Если эндпоинты блокируются, меняйте сначала `I1`, а junk параметры меняйте в крайнем случае.

По умолчанию `I1` имитирует запрос iCloud. WARPSCOUT умеет генерировать другие:

```sh
warpscout scan -p awg -gen-i1 quic
warpscout scan -p awg -gen-i1 dns -i1-sni example.com
```

`-gen-i1` принимает `quic`, `dns`, `sip`, `stun` или `random`. Начинать стоит с `quic`, потому что он чаще всего работает. `-i1-sni` задаёт имя хоста, которое упоминает поддельный пакет; без него берётся случайный известный хост. Можно также подсунуть сырой пакет через `-i1 PKT` или не отправлять никакого вообще через `-i1 none`.

### Мусорные пакеты

Ими управляют три числа:

| Флаг        | Значение                                             |
| ----------- | ---------------------------------------------------- |
| `-jc N`     | Сколько мусорных пакетов отправлять (по умолчанию 6) |
| `-jmin N`   | Наименьший размер мусорного пакета (по умолчанию 10) |
| `-jmax N`   | Наибольший размер мусорного пакета (по умолчанию 50) |
| `-gen-junk` | Выбрать все три случайно для этого запуска           |

В большинстве сетей сработают значения по умолчанию. Сами по себе они редко что-то разблокируют, так что всегда начинайте с `-gen-i1`.

Если не хочется подбирать параметры вручную, то [`find-junk`](#шаг-3-find-junk-только-если-всё-заблокировано) перебирает комбинации, пока что-нибудь не заработает.

## MASQUE

Cloudflare раздаёт WARP не только по WireGuard, но и по MASQUE.

```sh
warpscout scan -p masque
```

Пулов эндпоинтов нет. MASQUE отвечает ровно на двух anycast-адресах каждого семейства - `162.159.198.1` и `162.159.198.2`, `2606:4700:103::1` и `::2` - на фиксированном наборе портов (`443 500 1701 4500 4443 8443 8095`). Скан покрывает эти адреса, умноженные на эти порты.

Один и тот же `masque` эндпоинт с одним и тем же SNI может работать нестабильно, поэтому каждый эндпоинт проверяется минимум 3 раза. Это меняется флагом `-masque-attempts N`.

Все эндпоинты одного прогона выходят через **одну и ту же ноду**. Какая это нода, зависит от вашей сети, а не от выбранного эндпоинта, поэтому `-node` и `-country` при `-p masque` отвергаются.

### SNI

У MASQUE нет ни junk-пакетов, ни `I1`. Их аналог - SNI и его смена позволяет добиться стабильной работы:

```sh
warpscout scan -p masque -masque-sni www.apple.com
```

Без указания `-masque-sni` по умолчанию используется `consumer-masque.cloudflareclient.com`. Если с ним `-p masque` ничего не нашёл, то стоит попробовать другой `-masque-sni`.

### Регистрация и конфиги

`warpscout register` заводит MASQUE-аккаунт рядом с аккаунтом для WireGuard/AmneziaWG, потому что одно устройство не может быть и тем и другим.

`-conf` пишет `config.json` для usque, а не `.conf` и печатает команду запуска:

```sh
warpscout scan -p masque -conf usque.json
# usque socks -c usque.json -P 8443 -s www.apple.com
```

`-table-off`, `-mtu` и `-dns`/`-no-dns` не имеют аналога в `config.json` usque и здесь игнорируются - под `-conf-type mihomo` флаги DNS работают как обычно.

## Docker

Образ мультиархитектурный (`linux/amd64` и `linux/arm64`). Рабочая директория контейнера - `/data`, туда же кладётся файл аккаунта.

### Сохранить аккаунт между запусками

Примонтируйте директорию, иначе аккаунт умрёт вместе с контейнером и регистрироваться придётся каждый раз:

```sh
docker run --rm --user "$(id -u):$(id -g)" -v "$PWD:/data" vernette/warpscout register
docker run --rm -it --user "$(id -u):$(id -g)" -v "$PWD:/data" vernette/warpscout scan -p awg
```

> [!NOTE]
> Контейнер работает от root, поэтому без `--user` всё записанное в примонтированную директорию - файл аккаунта, отчёт, конфиг `-conf` - принадлежит root, а не текущему пользователю. `$(id -u)` - синтаксис шелла Linux и macOS. В Docker Desktop для Windows флаг не нужен: драйвер файловой системы сопоставляет владельца сам.

### Цвет и живая панель

И то, и другое включается, только когда вывод идёт в терминал, поэтому нужен `-it`: `-t` выделяет псевдотерминал, `-i` подключает стандартный ввод. Без `-i` ответы терминала на запросы панели никто не читает, и они утекают в шелл сырыми символами.

### Пинг внутри контейнера

На современном Docker делать ничего не надо, `ENDPOINT PING` работает из коробки. Если он показывает `?` (старый Docker, ужесточённые настройки по умолчанию, другой движок контейнеров), добавьте sysctl:

```sh
docker run --rm -it --sysctl net.ipv4.ping_group_range="0 2147483647" \
  -v "$PWD:/data" vernette/warpscout scan -p awg
```

`TUN PING` работает внутри туннеля и не требует привилегий ни в каком контейнере.

### IPv6 и выбор интерфейса

`-6` и `-I` требуют сети хоста. У контейнера своё сетевое пространство имён, интерфейсов хоста там нет, а IPv6 обычно выключен, поэтому запускайте с сетью хоста:

```sh
docker run --rm -it --network host -v "$PWD:/data" vernette/warpscout scan -p awg -6
docker run --rm -it --network host -v "$PWD:/data" vernette/warpscout scan -p awg -I eth0
```

### Собрать образ

```sh
# под свою систему
docker build -t warpscout .

# под другую платформу
docker buildx build --platform linux/arm64 -t vernette/warpscout:arm --load .
```

## Решение проблем

**`ENDPOINT PING` показывает `?`.** Это пинг до адреса эндпоинта, и ему нужен ICMP-сокет, который текущему пользователю разрешено открыть. `TUN PING` это не затрагивает никогда. На большинстве систем такое разрешение уже есть - и Debian 13, и современный Docker поставляются с открытым непривилегированным диапазоном, - так что сначала проверьте:

```sh
cat /proc/sys/net/ipv4/ping_group_range   # "0 2147483647" = разрешено, "1 0" = закрыто
```

Если закрыто, либо один раз выдайте бинарнику capability, либо откройте диапазон системно:

```sh
sudo setcap cap_net_raw+ep ./warpscout

# или
sudo sysctl -w net.ipv4.ping_group_range="0 2147483647"
```

Ни то, ни другое не является изменением кода, и без них ничего не ломается: колонка просто показывает `?`, а с `-tun-ping` для ранжирования остаётся `TUN PING`.

**Инструмент убивают на маленьком роутере.** На устройстве с 256 МБ памяти `-jt 10` по умолчанию может выесть всю память. Безопасны значения от 4 до 8:

```sh
warpscout scan -p awg -jt 6
```

**macOS отказывается запускать бинарник.** Снимите флаг карантина - см. [Установка](#установка).

**Всё падает с `-p wg`.** В фильтрующей сети это нормально. Попробуйте `-p awg`, а если и он не сработает - запустите `find-junk`.
